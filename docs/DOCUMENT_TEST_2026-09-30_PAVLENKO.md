# Тест документного контуру — ПАВЛЕНКО — 2026-09-30

## Clean test
Після повторного створення тестового кандидата `ПАВЛЕНКО Ростислав Сергійович` у `public.candidates` з'явився кандидат, але:
- `public.documents` не містив запису для його `candidate_id`;
- Storage bucket `candidate-documents` не містив файла під його `candidate_id`.

### Висновок
Обрив відбувався до фактичного запису рекомендаційного листа в Storage. Проблема не була лише в UI списку документів.

## Виявлена слабкість V2
V2 `document-type-field.js` умів зареєструвати файл, якщо файл уже був у Storage, але не міг відновити ситуацію, коли upload не відбувся.

## V3
30.09.2026 `document-type-field.js` оновлено.

Після створення кандидата repair-guard:
1. бере файл з `#recommendationFile.files[0]`;
2. перевіряє `<candidate_id>/recommendation/` у `candidate-documents`;
3. якщо файла немає — завантажує вибраний файл у Storage;
4. знаходить `requirement_id` для `Копія рекомендаційного листа`;
5. створює запис у `public.documents`;
6. встановлює `document_type = Рекомендаційний лист`;
7. встановлює `status = Завантажено`;
8. встановлює `processing_status = AI оброблено`;
9. встановлює `verification_status = Не перевірено`.

## Наступний тест
Після деплою V3 повторити створення тестового кандидата з тим самим рекомендаційним листом.

Перевірити три точки:
- Storage: один файл;
- `documents`: один запис;
- UI «Документи»: документ відображається та прив'язаний до кандидата.

## Архітектурне правило
Не використовувати `localStorage` для документів. Канонічний контур: `candidate-documents` → `public.documents` → `document_requirements` → OCR/AI → рекрутерська перевірка.
