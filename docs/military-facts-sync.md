# Автоматичне перенесення складних військових відомостей

Реалізовано локально, 16.10.2026. Чинну RPC-функцію прочитано через Supabase лише для перевірки визначення; робочі картки не змінювалися. Міграція й зміни Edge Function ще не застосовані.

## Охоплення

- Присяга: дата та частина.
- Присвоєння звання: звання, дата, частина, видавець і номер/дата наказу.
- Звільнення: частина, підстава, номер і дата наказу.
- Нагороди: назва, підстава за наявності, видавець, номер і дата наказу.
- Бойові періоди: місце, початок і завершення з підтвердного документа.
- Збори в запасі: дати, частина, посада, ВОС за наявності, наказ.

Перевірку виконує спільний модуль supabase/functions/_shared/military-facts.js. Він не викликає AI та не записує дані. Збереження виконує чинний захищений RPC через document-ai-sync.js. Оновлений prompt ai-classify-document просить потрібні структури, сторінки та дослівні цитати.

## Прийняття даних

Для автоматичного прийняття потрібні впевненість не нижче 0,85 (або підтверджений рекрутером документ), звірений власник, повні коректні дати, необхідні реквізити, сторінки й читабельна цитата. Це технічний поріг, а не гарантія істинності розпізнавання. УБД не є джерелом конкретних бойових періодів. Нечіткі, закреслені, частково датовані чи неповні записи передаються рекрутеру.

Дату у старому military_rank_records.date чинний OCR-контракт трактує як дату наказу в таблиці присвоєння; її дозволено зіставляти з order_date. Нові різні дати повертаються окремо. Відсутні дати не обчислюються з сусідніх рядків.

Видавець наказу, коли джерело містить лише частину, зберігається як код цієї частини. Імена командирів або розшифрування організації не вигадуються.

## Захист даних

Масиви доповнюються новими записами. Старі елементи, включно з ручними підтвердженнями, повинні залишатися незмінним префіксом. Однакові повтори не додаються; відмінності в уже відомому записі стають питанням до рекрутера. Присяга й звільнення заповнюються лише за відсутності збережених відомостей. Явне «не служив» не переписується: суперечливі дані присяги, звільнення та бойових періодів затримуються для звірки.

Зберігаються source_document_id, source_pages, raw_text та source_record_index. Ознака accepted_by_ai відрізняється від confirmed_by_user; AI не може встановити ручне підтвердження. Наказ до чинного звання з однозначного прийнятого запису може використовуватися в послужному без підміни ручного підтвердження.

RPC перевіряє активного працівника, RLS, версію документа, expected_ai та expected_current, незмінність старих елементів, тип джерела, рівень впевненості, сторінки, цитату й відповідність значень оригінальній структурі AI. Старі клієнти з guard version 1 залишаються сумісними; нові записи використовують version 2. Старий сервер відхиляє version 2 до будь-якого запису.

2. Застосувати supabase/migrations/20261016062606_safe_military_document_sync.sql через штатний механізм міграцій. Нові таблиці або колонки не створюються, historical backfill не запускається.
3. Оновити ai-classify-document і клієнтські модулі разом із новим script shared/military-facts.js.
4. Історичні документи переносити лише після перегляду конкретного звіту. Для неповних старих OCR-даних може знадобитися повторне розпізнавання.

Знімок попередньої RPC для відкату: supabase/rollback/safe_military_document_sync.sql. Відкат коду не видаляє вже збережені факти. Спочатку повернути попередній клієнт version 1, потім за потреби попередню функцію. Старі клієнти version 1 сумісні з новою функцією.

## Перевірка

JavaScript-регресії перевіряють шість структур, походження даних, відсутність дублів, нечіткі записи, збереження ручних фактів і перевірку власника.

SQL-міграція скомпільована й виконана в ізольованому PostgreSQL/WASM PGlite 0.5.10. Пакет отримано з офіційного npm-реєстру й перевірено за SHA-512; це лише тимчасова тестова залежність, не залежність CRM. Виконано 10 SQL-сценаріїв: старий сервер відхиляє новий guard; прийняття шести структур; незмінність ручного запису при доповненні; відмова при підроблених значеннях або сторінках; контроль конкурентного запису; сумісність guard 1; неактивний працівник; обмеження RLS. Це перевірка контрольної схеми, а не копія всіх виробничих політик.

Тест: tests/crm-military-sql.cjs. Можна вказати CRM_PGLITE_MODULE для локального шляху до перевіреного PGlite. Робоча база в тестах не використовується.


Загальний підсумок цієї зміни: 52 JavaScript-перевірки та 10 сценаріїв ізольованого PostgreSQL пройдені. Повторно пройдені звіт у браузері й 37 перевірок сумісності V3. Живий AI-запит із документами кандидата не виконувався; старі OCR-відповіді без сторінок і цитат залишаться для звірки або повторного розпізнавання.
