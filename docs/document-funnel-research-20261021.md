# Дослідження зв’язків документів для послужного — 21.10.2026

## Межі дослідження
Лише SELECT до робочої БД та читання коду. Без повторного OCR, змін записів і публікації. Первісний широкий запит повних карток/OCR не був дозволений автоматичною перевіркою; висновки спираються на агреговані дані та структуру, без перегляду всіх сканів. Підрахунки варіантів не доводять фактичних помилок.

## Фактичний стан
105 невидалених записів, 10 candidate_id; 67 записів з ai_extracted. Після вибору останньої версії за candidate_id + version_group_id (або id), version_number і created_at — 100 записів. 5 записів мають version_number > 1. У 5 групах candidate_id + document_type є кілька актуальних документів. file_hash заповнений у 0 активних записів: відсутність знайдених дублікатів за хешем нічого не доводить. 3 останні документи мають різні document_type та ai_document_type; це може бути уточнення класифікації, а не помилка. У 10 актуальних РЛ є вкладені personal/service.

Груба звірка лише непорожніх верхньорівневих рядкових полів після latest-version: ПІБ — 7 багатоджерельних справ, 4 з різними текстами; дата народження — 7/2; місце народження — 5/5; РНОКПП — 6/1. Вкладені поля тут не враховані. Історичні прізвища, формат дат, скорочення та помилки власника ще не розділені; це черга перевірки, не список доведених конфліктів.

## Надійні та ймовірні зв’язки
| Джерела | Що зіставляти | Правило |
|---|---|---|
| Паспорт/ID + РНОКПП | Особу, номер, дату народження | РНОКПП — власника; не номер іншого посвідчення |
| Народження + зміна ПІБ + паспорт | Старе → нове ПІБ, дату народження | Окремі події зміни, без переписування історії |
| Народження + автобіографія | Батьків | Роль + ПІБ + доступні дати; адреса батьків окрема |
| Шлюб + паспорт + автобіографія | Подружжя, прізвище до/після шлюбу | Спочатку визначити кандидата серед учасників |
| Диплом + додаток + автобіографія | Освітню подію | Заклад, номер диплома, рівень, період; кілька дипломів дозволені |
| Трудова + ПФУ + автобіографія | Періоди та характер роботи | Відділити неофіційну діяльність, не виводити посаду з суми внесків |
| Військовий + Резерв+ + накази | Звання та події служби | Кожне значення має дату чинності; наказ — тип події та видавця |
| Військовий + автобіографія | Хронологію | Часткові дати не доповнювати вигаданим днем |
| Витяг проживання + паспорт + автобіографія | Адреси | Реєстрація, фактичне проживання й адреси родичів — різні факти |

## Небезпечні та абсурдні зв’язки
- ШПК з РЛ → чинне військове звання; бажана частина → колишнє місце служби.
- УБД → конкретні бойові періоди, ВОС або факт поранення.
- ВЛК → дата початку служби; Додаток 13 → доведений висновок ВЛК.
- Місце народження → фактична адреса; адреса матері → адреса кандидата.
- Зміна прізвища кандидата → автоматична зміна прізвищ батьків.
- Прізвище дружини/дитини → чинне ПІБ кандидата.
- Посада → ВОС за припущенням; БЗВП → вища військова освіта.
- Посвідчення водія/тракториста → паспортні реквізити.
- Служба в поліції → військове звання або вигадана військова частина. За прийнятим правилом CRM поліція друкується в розділі служби з окремим kind=police_service.
- Згенерований CRM послужний/анкета → незалежне підтвердження даних, з яких вони створені.
- Повторний OCR одного скану, повторне завантаження чи дві моделі → два незалежні докази.
- Прапорець «є без файла» → підтверджений зміст документа.

## Конкретні структурні знахідки
1. Свіжий неопублікований document-crosscheck.js використовує version та file_sha256 замість version_number та file_hash. Групує за requirement_id/типом і тому ризикує втратити окремі актуальні дипломи. Потрібне групування саме версій, не типів.
2. 8 education_records мають source_pages, але не стандартний raw_text; 19 work_events мають цитати і сторінки; 8 military_service_records не мають raw_text або page/source_pages. В інших ключах можуть бути посилання — потрібна нормалізація, не твердження про повну відсутність доказів. source_document_id у цих OCR-масивах не заданий: його слід надійно успадковувати від документа-контейнера.
3. Два родичі використовують relation замість relationship. Це не відсутність спорідненості; поточний merge вже має fallback, нові порівняння також повинні його враховувати.
4. Непорожнє passport_data є в одному освітньому документі, одному посвідченні тракториста та чотирьох витягах проживання. У витягу можуть бути посилання на паспорт; без скану не визначено, де помилкова класифікація номера. document-data-policy вже блокує паспортні поля сторонніх типів — цю межу зберегти.
5. Однакова універсальна схема містить багато null-полів різних типів. Наявність ключа не є фактом і не доводить абсурдного зв’язку. Аналізувати лише непорожні валідні значення з контекстом.
6. candidate-field-registry описує service.records лише як military_service, тоді як генератор уже друкує military_service + police_service. Контракт треба узгодити з чинною реалізацією.
7. service_record_print перекриває рассчитані поля в генераторі. Тому виправлена картка не гарантує оновленого друку: потрібна перевірка застарілих друкованих правок.
8. Наявний диплом повністю вимикає fallback bio_education_claims. Автобіографія може містити інший, не дубльований рівень освіти; потрібне зіставлення подій, а не глобальне відкидання біографії.

## Рекомендована воронка
Документ → роль особи → факт/подія → джерело (документ, версія, сторінка, цитата/зона) → зіставлення з незалежними джерелами → чинне значення або історія → поле послужного.

Для факту зберігати subject (кандидат/мати/батько/подружжя/дитина), тип, значення, точність дати, період чинності, походження й рішення. Стан: одне джерело / підтверджено незалежним джерелом / історична зміна / суперечність / невизначено / відхилено. Це концептуальний контракт, не вже створена схема БД.

## Черговість реалізації
1. Виправити версії, ідентифікатори файлів, aliases і вкладені формати перед публікацією crosscheck.
2. Нормалізувати ролі людей та історію ПІБ. Розібрати кандидати на розбіжності без масового перезапису.
3. Зіставляти освіту, роботу, службу як окремі події, не як один текст.
4. Перевіряти кожне поле послужного разом із друкованою правкою і джерелом.
5. Для навчання допускати лише перевірені примери з незалежним походженням; виключати створені CRM документи та повторний OCR одного файла. Історичні суперечності не закривати автоматично.
