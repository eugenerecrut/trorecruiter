# Єдиний контракт фактів — shadow reader, етап 2

## Призначення

`candidate-facts.js` підключений до реального монтування картки у `candidate-card-v3.js`. Він читає наявний snapshot і план `CRMIntake.items`; не змінює writers, RPC, OCR, схему, друковані шаблони або прийняті значення. Чинні перевірки й лічильники лишаються основними.

Увімкнення лише діагностики: `?compactCaseView=1&factsShadow=1` або `window.CRMFeatureFlags.factsShadow=true`. За замовчуванням вимкнено; явний false блокує URL opt-in. Параметр не впливає на дозволи чи запис у БД. У картці з’являється згорнута службова секція «Діагностика джерел (без запису)»; відкриття джерела використовує чинний `openDocument`.

До вже наявної вибірки журналу додано `id,candidate_id`, щоб reader міг перевірити належність receipt ідентифікованій картці. Фільтр candidate_id, ліміт 250, RLS та кількість мережевих запитів не змінюються.

## API

`CRMCandidateFacts.build({candidate, personalFile, documents, requirements, activity, comparison})` — синхронний reader без мережевих викликів. Дані копіюються до виклику чинних planner/policy, тому їхня нормалізація не змінює аргументи caller.

Вихід: `version`, `snapshotId`, `facts`, `claims`, `issues`, `decisions`, `diagnostics`, `coverage`, `shadow`. `comparison.conflictCount` — необов’язковий результат чинного звіту; reader обчислює delta, не коригуючи жоден лічильник.

### Факти та джерела

- Початкове покриття: явні identity/contact/recruitment/absence шляхи, групи чинного `CRMFieldRegistry`, поля записів relatives/education_records/work_records/work_events.
- Composite-група не перетворюється на один скаляр. Невідомі ключі записів залишаються в unmappedLocations, а рядки requires_review/crossed_out мають held=true. Відмінні legacy-шляхи дають diagnostics, не мовчазне об’єднання.
- Непорожнє значення захищене навіть без provenance. Відсутність історії не позначається як «внесено вручну».
- `human_confirmed` вказує лише на наявну явну ручну позначку в legacy metadata; renderer називає її саме позначкою, не перевіркою особи працівника.
- `documented` означає явне посилання на придатне джерело або точний activity receipt. Це не новий дозвіл на автоматичний запис і не незалежна перевірка правдивості.
- accepted_by_ai не стає human_confirmed. Нерозбірливе/невизначене походження не заповнюється припущеннями.
- Значення claims беруться з чинного planner (`rawValueOrigin=existing-planner-proposal`), а не оголошуються дослівним OCR оригіналу. Колекційна пропозиція може містити вже збережені рядки; вона не підтверджує їх незалежно цим документом.
- Для невідомих сторінок, зон і run ID повертаються порожній масив/null, а не вигадані значення.
- Дані з активного snapshot із same candidate ID; чужі, generated, видалені, замінені та джерела merged/archive картки не використовуються як нові твердження. Власницький конфлікт planner демотує source-reference до unknown provenance.
- version/hash/storage keys збережені для кореляції. Вони не перетворюються на лічильник незалежних підтверджень.

### Записи та рішення

entityRef для масивів прив’язаний до snapshot; persisted UUID не додаються. Зіставлення матері/родичів залишається у чинному planner: повніше ПІБ лише пропонується, ручні значення захищені, неоднозначний збіг лишається питанням колекції.

Наявні `_crm_review_decisions` читаються точним порівнянням target/key/current/incoming/reason і маркерами reviewed_by/at. Рішення не підтверджує фактичну істинність значення. Для старих записів відсутній повний source snapshot: `sourceBinding=container-only` і окремий diagnostic. Зниклий з нового плану ключ залишається в історії як `not-in-current-plan`. Reader не видає нових дозволів на застосування цих рішень.

Opaque ID/hash використовується лише для display references, не для CAS, авторизації або перевірки рішення. Правильність рішення перевіряється точними значеннями. Жоден новий writer не використовує ці ID.

## Межі

Це перший реалізаційний коміт, не завершена міграція всіх полів CRM. `coverage.unmappedLocations` явно показує непокриті поля; оригінальні дані не очищуються й не втрачаються. Документи обмежені наданим snapshot, журнал може бути неповним. Нові моделі не підміняють друковані значення. Частковий planner fallback позначається diagnostic.

## Перевірка та відкат

- `node --test tests/crm-candidate-facts.cjs` — реальні planner/policy, незмінність входів, idempotence, захист ручних полів, родичі, джерела, stale-рішення, provenance, типи періодів, renderer.
- Чинний CI-набір збережено; додано нові тести.
- `tests/crm-compact-case-browser.cjs` — стандартний, компактний та компактний+shadow режими; по 36 наявних сценаріїв збереження/CAS, перевірка видимості службової секції та PDF-кнопки.

Відкат: прибрати `factsShadow=1` / явний flag false. БД відновлювати не потрібно. Чинний маршрут зіставлення і генератори не змінені. Перед будь-яким перенесенням реальних даних потрібні окремі preview і погодження.

### Доповнення покриття
Структуровані записи про присвоєння звань, бойові дії, нагороди та збори в запасі розкладаються на окремі поля зі збереженням джерела й ознаки перевірки. Номери наказів і часткові дати зберігаються дослівно. У періодах діяльності окремо враховано locality та disposition. Невідомі ключі залишаються у звіті непокритих полів. Додано дві регресійні перевірки; локальний набір адаптера — 19/19.

Друковані правки service_record_print виділено в окремий printOverrides: вони не є фактами чи доказами. Невідомі ключі та нестрокові значення дають діагностику; збережені значення не змінюються. 20 тестів адаптера.

Присягу, звільнення в запас і реквізити шлюбу розкладено на поля. Підтримано об’єкти та збережений JSON-рядок, як у чинному генераторі. Невідомі поля та пошкоджені структури залишаються у діагностиці, вхідні дані незмінні. Набір адаптера: 22 перевірки.

Перевірка сумісності: старе relation використовує чинний fallback relationship/relation; суперечливі значення дають legacy-path-divergence. Масиви, null і примітиви всередині колекцій позначаються invalid-record та залишаються непокритими. 24 тести адаптера, три браузерні режими по 36 сценаріїв, помилок JS немає (синтетичні дані).

Пряма інтеграційна звірка з CRMServiceRecord.model: вихідна модель послужного до та після shadow-читання збігається побайтово; джерельні реквізити наказу, присяги, звільнення і шлюбу присутні у відповідних друкованих полях. Held-записи служби та нагород лишаються у діагностиці й виключаються чинним генератором. Перевірка моделі не є візуальною перевіркою PDF. 26 тестів адаптера.

Наступне покриття (після 1.2.9): паспортні реквізити, УНЗР, громадянство, стать, додатковий телефон, email, messenger, зареєстрована/фактична адреси, кількість і відомості про дітей. Лише збережені значення: UI-default громадянства не стає фактом; 0 дітей не губиться як порожнє. Суперечливі адресні fallback збережено в діагностиці. Набір адаптера — 28 тестів.
