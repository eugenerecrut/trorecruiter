# Аудит контуру документів — 2026-09-30

## Факти, перевірені в коді та Supabase

### 1. Реальне сховище
- Supabase Storage bucket: `candidate-documents`.
- `documents.js` завантажує файли за шляхом `<candidate_id>/incoming/<unique_filename>`.
- Окремий шлях нового кандидата зберігає рекомендаційний лист за `<candidate_id>/recommendation/<unique_filename>`.
- У Storage фактично є файли, тобто завантаження в bucket працює.

### 2. Реєстр документів
Таблиця `public.documents` існує, має RLS і зовнішні ключі до `candidates` та `document_requirements`.

На момент первинного аудиту: **0 рядків у `documents`**.

Отже, проблема «файл є у Storage, але не видно в списку документів» була реальною: Storage і реєстр документів могли розходитися.

### 3. Код, який додає документи через розділ «Документи»
`documents.js` має повний `processOneDocument()`:
1. upload у Storage;
2. OCR;
3. AI classification;
4. формування запису;
5. `documents.insert(...)`;
6. у разі помилки реєстрації видаляє файл із Storage.

Цей шлях є базовою канонічною реалізацією.

### 4. Код створення нового кандидата
`script.js` має окремий шлях `uploadRecommendation()`.
Він:
1. завантажує рекомендаційний лист у Storage;
2. вставляє запис у `documents`.

Початковий запис мав `document_type: 'Рекомендаційний лист'`, але не передавав `requirement_id` і не задавав явно статуси.

### 5. Виявлена невідповідність типів
У `document_requirements` фактичний обов'язковий тип:
`Копія рекомендаційного листа`

У `script.js` для нового кандидата записується:
`Рекомендаційний лист`

У `documents.js` список документів зіставляє документ із вимогою через:
`requirement_id === r.id || document_type === r.document_type`.

Це створювало ризик, що документ не буде віднесений до потрібного рядка комплекту.

### 6. Виявлена проблема зі схемою MIME
`public.documents.mime_type` має CHECK:
`mime_type IS NULL OR mime_type = 'application/pdf'`.

Водночас `documents.js` дозволяє завантажувати PDF, JPG, JPEG, PNG, DOC, DOCX і передає фактичний MIME у `documents.insert`.

Отже, для JPG/PNG/DOC/DOCX вставка в `documents` суперечить обмеженню таблиці. Storage при цьому може прийняти файл, а запис у `documents` — ні.

### 7. RLS
Для `documents` існують policies:
- authenticated recruiters can create documents;
- view documents;
- update/delete з обмеженнями.

INSERT policy дозволяє authenticated користувачу створювати документ. RLS сама по собі не пояснювала 0 рядків.

### 8. Фактичний стан кандидата Павленка
У Supabase існує кандидат `ПАВЛЕНКО Ростислав Сергійович`.
Під час перевірки для його `candidate_id` у `documents` не було запису.
У Storage при цьому існують об'єкти в його каталозі `incoming`, що підтверджує можливість розходження Storage/реєстру в історичних тестах.

### 9. Внесена зміна 2026-09-30
Файл `document-type-field.js` оновлено до V2.
Додано repair-guard після створення кандидата:
- перевіряє, чи існує запис `documents` типу `Рекомендаційний лист`;
- якщо запису немає, шукає файл у `<candidate_id>/recommendation/`;
- знаходить `requirement_id` для довідникового типу `Копія рекомендаційного листа`;
- створює канонічний запис у `public.documents`;
- ставить `status = 'Завантажено'`;
- ставить `verification_status = 'Не перевірено'`;
- ставить `processing_status = 'AI оброблено'`.

Це **страхувальний механізм**, а не заміна основного document pipeline.

## Робоча модель
`Файл → Storage → documents → requirement → OCR/AI → рекрутерська перевірка → підтверджений статус`

Storage не вважається достатнім доказом наявності документа в особовій справі. Канонічний реєстр — `public.documents`.

## Наступні технічні дії
1. Перевірити новий сценарій «Нова особова справа» на реальному рекомендаційному листі.
2. Перевірити, що після збереження кандидата в `documents` з'являється один запис.
3. Перевірити `requirement_id` → `Копія рекомендаційного листа`.
4. Перевірити відображення документа у списку «Документи».
5. Узгодити канонічну назву `document_type` без дублювання термінів.
6. Усунути конфлікт MIME CHECK між БД і frontend.
7. Перевірити, що підтвердження рекрутером реально записується в БД.
8. Додати контроль сирітських Storage-файлів.

## Важливе правило
Не створювати паралельний localStorage-механізм. Існуючі `documents.js`, `candidate-documents`, `documents` та `document_requirements` є базовим контуром.
