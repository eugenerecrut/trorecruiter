# Аудит контуру документів — 2026-09-30

## Факти, перевірені в коді та Supabase

### 1. Реальне сховище
- Supabase Storage bucket: `candidate-documents`.
- `documents.js` завантажує файли за шляхом `<candidate_id>/incoming/<unique_filename>`.
- У Storage фактично є файли, тобто завантаження в bucket працює.

### 2. Реєстр документів
Таблиця `public.documents` існує, має RLS і зовнішні ключі до `candidates` та `document_requirements`.

На момент аудиту: **0 рядків у `documents`**.

Отже, проблема «файл є у Storage, але не видно в списку документів» реальна: Storage і реєстр документів зараз можуть розходитися.

### 3. Код, який додає документи через розділ «Документи»
`documents.js` має повний `processOneDocument()`:
1. upload у Storage;
2. OCR;
3. AI classification;
4. формування запису;
5. `documents.insert(...)`;
6. у разі помилки реєстрації видаляє файл із Storage.

Цей шлях є правильною базовою реалізацією.

### 4. Код створення нового кандидата
`script.js` має окремий шлях `uploadRecommendation()`.
Він:
1. завантажує рекомендаційний лист у Storage;
2. окремо вставляє запис у `documents`.

Поточний запис має `document_type: 'Рекомендаційний лист'`, але **не передає `requirement_id` і не задає явно статуси**.

### 5. Виявлена невідповідність типів
У `document_requirements` фактичний обов'язковий тип:
`Копія рекомендаційного листа`

У `script.js` для нового кандидата записується:
`Рекомендаційний лист`

У `documents.js` список документів зіставляє документ із вимогою через:
`requirement_id === r.id || document_type === r.document_type`.

Тому два різні текстові значення створюють ризик, що документ не буде віднесений до потрібного рядка комплекту.

### 6. Виявлена проблема зі схемою MIME
`public.documents.mime_type` має CHECK:
`mime_type IS NULL OR mime_type = 'application/pdf'`.

Водночас `documents.js` дозволяє завантажувати PDF, JPG, JPEG, PNG, DOC, DOCX і передає фактичний MIME у `documents.insert`.

Отже, для JPG/PNG/DOC/DOCX вставка в `documents` суперечить обмеженню таблиці. Storage при цьому може прийняти файл, а запис у `documents` — ні.

Це критична розбіжність між frontend і схемою БД.

### 7. RLS
Для `documents` існують policies:
- authenticated recruiters can create documents;
- view documents;
- update/delete з обмеженнями.

INSERT policy дозволяє authenticated користувачу створювати документ. Тому наявність RLS сама по собі не пояснює 0 рядків.

## Робоча модель, яку закріплюємо
`Файл → Storage → documents → requirement → OCR/AI → рекрутерська перевірка → підтверджений статус`

Storage не вважається достатнім доказом наявності документа в особовій справі. Канонічний реєстр — `public.documents`.

## Наступні технічні дії
1. Узгодити канонічну назву типу рекомендаційного листа з `document_requirements`.
2. Після створення кандидата створювати `documents` через єдиний документний pipeline.
3. При створенні документа завжди встановлювати `requirement_id`, якщо тип знайдений у довіднику.
4. Усунути конфлікт MIME CHECK: або дозволити всі підтримувані формати в БД, або обмежити frontend лише PDF. Для CRM особової справи правильним напрямком є узгодити БД з фактично підтримуваними форматами.
5. При помилці `documents.insert` не залишати сирітський файл у Storage.
6. Додати перевірку після створення кандидата: `documents` має містити рекомендаційний лист, якщо файл був завантажений.
7. Додати статуси: `Завантажено` → `AI оброблено`/`Розпізнано` → `Підтверджено`.

## Важливе правило
Не створювати паралельний localStorage-механізм. Існуючі `documents.js`, `candidate-documents`, `documents` та `document_requirements` є базовим контуром.
