# Ревізія CRM — 5 жовтня 2026

## Обсяг

Перевірено зв’язки candidates → personal_files → documents → document_requirements → Storage, відображення картки, збереження полів, етапи / паузи, умови документів, формування PDF «Анкета», навігацію та мобільне компонування. Базою був актуальний main.

## Перевірка даних

- 1 кандидат і 1 особова справа; дублів personal_files немає.
- 25 записів документів, з них 1 видалений; 24 активні файли.
- Немає документів без кандидата, з відсутнім requirement_id або з посиланням на неіснуючу вимогу.
- Усі активні storage_path мають відповідний об’єкт у candidate-documents.
- Не знайдено конфліктів sex / served_before між основними полями та profile_data.
- Активних документів зі статусом «AI помилка» на момент перевірки немає. Це перевірка збережених результатів, а не новий OCR усіх оригіналів.

## Виправлення

| Проблема | Ремонт |
|---|---|
| Частина реквізитів освіти була у формі, але відсутня у profileKeys | Зберігаються код спеціальності, дати навчання, реквізити диплома та додатка |
| Картка могла перезаписати зміни іншого працівника | UPDATE перевіряє версію updated_at, завантажену з карткою; нуль оновлених рядків залишає форму без втрати чернетки |
| Зміна етапу могла загубитися при збереженні картки | Чернетка форми етапу відновлюється після оновлення панелі; перехід попереджає про незбережені зміни |
| Зміна статі скидала сімейний стан | Зберігається значення married / divorced / single з відповідною формою слова |
| latest порівнював між собою документи без групи версій | Порівняння виконується лише всередині визначеної version_group_id |
| Фото могло братися зі старої або видаленої версії | Картка та Обов’язкова інформація беруть актуальні невидалені документи |
| Помилка API виглядала як порожня база | Завантаження кандидатів, документів і вимог повертає помилку; головна сторінка повідомляє про збій |
| Головна показувала усі версії та видалені документи | Лічильник показує актуальні невидалені файли; під час завантаження показано «…», при помилці — «—» |
| Рекрутер на головній брався з іншого поля | Використовується responsible_recruiter_id та довідник crm_staff |
| Завантажений, але неперевірений файл виглядав готовим на головній | Комплектність головної враховує підтвердження документа |
| Для пакета показувалася лише перша помилка | Один список показує готовність усіх пунктів і дає перехід до документів; формування заблоковане за наявності проблем |
| УБД, нагороди та витяги з наказів блокували повний комплект | В інтерфейсі враховуються за наявності згідно з попередньо погодженими критеріями; дані вимог у БД не переписані |
| Етап займав перший екран телефону | На мобільному панель «Рух справи» спочатку згорнута; стан видно у заголовку. На комп’ютері панель відкрита |
| Перегляд пакета писав «Збережено», хоча збереження не відбулося | Повідомлення змінене на «Готово» |

Головна також показує справи на паузі з контрольною датою сьогодні або раніше. Дата визначається для Europe/Kyiv.

## Перевірки

`node tests/crm-audit.cjs` перевіряє синтаксис усіх кореневих JS та сценарії:

- ID-картка замість паспорта.
- Військовий квиток, приписне, посвідчення про приписку, Резерв+.
- Пріоритет військового квитка перед приписним.
- Відсутність кожного обов’язкового пункту, зокрема форми 13.
- УБД / посвідчення водія за наявності.
- Непідтверджений військово-обліковий документ блокує формування.
- Версії документів і видалення останньої версії.
- Збереження реквізитів освіти та конфлікт одночасного редагування.
- Умови для справ ВЧ, трудової діяльності та шлюбу.

Тести використовують синтетичні дані та макети API, не записують дані у Supabase. Виконано кілька проходів; синтаксис та сценарії пройшли.

На живій справі перевірено список кандидатів, картку, поля освіти та список готовності пакета. Пакет бачить усі обов’язкові файли, включно з ID-карткою, приписним і формою 13. Перевірено ширини 1366 та 390 px: діалог пакета вміщується в область сторінки. Скріншоти з особистими даними збережені локально, не в репозиторії.

## Межі та окремі питання

- Архівування зі знищенням оригіналів не запускалося на реальному кандидатові. У журналі немає архівних справ, тому такий повний сценарій потребує окремої тестової справи.
- candidates і personal_files зберігаються двома запитами. При збої другого запиту CRM повідомляє про часткове збереження. Повної транзакційності цей ремонт не вводить.
- Повторне формування пакета створює новий файл Storage; очищення попередніх пакетів — окреме питання зберігання.
- Не виконувалося нове платне AI/OCR усіх файлів та фізична перевірка камери / автофокусу на телефоні.
- Назва файла не доводить зміст документа. Підтвердження документа залишається ручною відповідальністю рекрутера.
- MIME CHECK не змінювався.

Supabase Advisors повернув попередження: search_path двох функцій, права EXECUTE на функції SECURITY DEFINER, вимкнена перевірка скомпрометованих паролів. Вони не є доказом фактичного витоку. Налаштування доступу в цьому ремонті не змінювалися; потрібна окрема перевірка призначення кожної функції.
