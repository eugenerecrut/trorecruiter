# Локальний кодер Qwen

Це пам’ять проєкту для `qwen2.5-coder:7b` в Ollama. Ваги моделі не змінюються. Перед кожним завданням інструмент додає [перевірені правила](knowledge.md) і [приклади з посиланнями на тести](examples.md). Поточна версія пам’яті — 3. Відповідь залишається пропозицією: модель не виконує команди, не редагує файли й не має доступу до CRM або БД.

Запуск з кореня робочого репозиторію:

```powershell
node tools/qwen-collaborator.mjs --task "Напиши тест для збереження ручного номера; selections використовує key"
node tools/qwen-collaborator.mjs --task "Перевір вузьке правило повної назви витягу ПФУ" --file work-document.js --dry-run
```

`--dry-run` перевіряє контекст без виклику моделі. Приймаються лише явно вказані відстежувані вихідні файли всередині репозиторію; tmp, backups, reports, .env і службові каталоги відхиляються. Є перевірка відомих форматів ключів, але вона не замінює перевірку вмісту: не додавайте персональні дані, документи кандидатів або секрети навіть у текст завдання. Відстежуваний файл теж може містити приватні відомості — відповідальність за добір контексту залишається на операторі.

Адреса фіксована: `127.0.0.1:11434`, модель фіксована й локальна. Один запит, без fallback, автоматичних повторів і виконання відповіді. Ліміт контексту — 16 000 символів, очікування — 120 секунд. Коли контекст завеликий, його не обрізають мовчки.

Результат і метадані зберігаються в `tmp/qwen-runs/` зі статусом `unreviewed`; ці файли не публікують і не додають до Git. Сирі відповіді не потрапляють у knowledge.md автоматично. Після перевірки тестами підтверджене виправлення можна окремо внести до бази знань через звичайний code review.

Для перевірки користі повторюйте однакові невеликі завдання, порівнюйте правильність із пам’яттю та без неї. Один успішний запуск не доводить загальне покращення моделі. Донавчання ваг — окремий майбутній процес.

## Контрольні вправи

```powershell
node tools/qwen-exercises.mjs --dry-run
node tools/qwen-exercises.mjs
```

Один локальний запит із десятьма синтетичними вправами, без документів кандидатів. Відповідь перевіряється як точний JSON із примітивними значеннями; самооцінка моделі, зайві поля, вигадані схеми, відсутні відповіді чи неправильні типи не зараховуються. Невдалий контроль повертає код 2, технічний збій — 1. Звіт має статус `diagnostic-not-approval` і зберігається локально в `tmp/qwen-runs/`. Код відповіді ніколи не виконується.

Контроль перевіряє правила, прямо описані в пам’яті. Це тренувальна діагностика, не незалежний benchmark програмування, не A/B-доказ покращення і не дозвіл автоматично змінювати CRM. Реальна перевірка 26.10.2026 із пам’яттю v2: 9/9; цей результат не замінює регресійні тести конкретної зміни.

## Як додавати знання

1. Зафіксувати конкретну помилку Qwen без особистих даних або секретів.
2. Перевірити її виконанням реального коду чи регресійним тестом.
3. Додати правильний і неправильний приклади та посилання на тест до examples.md.
4. Збільшити версію пам’яті в knowledge.md та KNOWLEDGE_VERSION, додати відповідну вправу й перевірки оцінювача.
5. Перевірити контекст через dry-run і виконати окремий контроль. Не копіювати неперевірені відповіді в знання автоматично.

Пам’ять v3 додає перевірений приклад розмежування роботи та служби (PR #170) і контрольне запитання про police_service. Початкова відповідь Qwen у цьому випадку була неправильною; після конкретного пояснення він виправив її. Це діагностика засвоєння контексту, а не доказ загального покращення.

Контроль v3 від 26.10.2026: 10/10 синтетичних відповідей правильні після додавання прикладу до контексту. Сирий локальний звіт збережений у tmp/qwen-runs; він не публікується. Результат не є незалежним тестом програмування.
