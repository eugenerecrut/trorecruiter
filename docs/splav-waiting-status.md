# СПЛАВ: файл очікує запуску та серверна черга

`processing_status='AI очікує'` означає, що розпізнавання не розпочате. Цей статус може залишитися після збереження файла та відмови enqueue (наприклад, коли черга вимкнена). Сам по собі він не доводить наявності запису в durable queue.

`CRMDocumentState.fileState(document, aiEnabled, queueJob)` розрізняє невідомий стан, підтверджену відсутність доручення (`null`), queued/running та термінальні стани. Лише RPC-підтвердження для точного document_id дозволяє показати «У черзі СПЛАВ». Однакові file_name не зіставляються як один документ.

Після `crm_splav_candidate_jobs` менеджер оновлює маркери тільки активної справи. RPC відбирає доручення за актуальними storage_path та ai_processed_at. При втраті відповіді або неправильному форматі немає твердження, що файл переданий чи що черга підтверджено порожня. Окремо показується кількість файлів без серверного доручення.

Для непереданого waiting-файла в компактному вигляді є видима кнопка «Передати СПЛАВ». Використовується чинний retry/enqueue шлях: для файла без OCR у стані «Завантажено» або «AI очікує» це перший повний делегований прохід, без повторного завантаження. Підтверджене поточне доручення блокує дубльоване натискання; RPC зберігає серверну ідемпотентність. Неоднозначна відповідь enqueue не запускає альтернативний платний виклик.

Виправлення не додає backfill усіх waiting-файлів і не вважає сам статус файлу новим дозволом на обробку. Потрібна явна дія користувача над конкретним документом. Історія, підтвердження та raw OCR не скидаються.

Перевірки: `tests/crm-splav-waiting-status.cjs`, чинні upload-pipeline/compact tests та `tests/splav-waiting-status-fixture.html`. Fixtures використовують синтетичні файли й імітацію RPC, без OCR та production-запитів.
